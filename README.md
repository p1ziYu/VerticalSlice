# GDIM33 Vertical Slice
## Milestone 1 Devlog
1. The graph is responsible for dynamically generating and displaying player choices during the narrative. When the dialogue engine reads a [Choice] command from the script, it uses a String Split node to break the single line of text into an array of separate data points. The graph then uses List: Get Item nodes to extract specific segments, which contain the actual text for options. These extracted strings are fed directly into TextMeshPro: Set Text nodes to update the UI buttons. Finally, the execution flow triggers a Game Object: Set Active node targeting the choicePanel variable, making the entire choice interface visible to the player.
2. In the new breakdown, I specified the NPC's internal logic by expanding it into an "Emotion State Machine". It works by executing specific logic within each state block. For example, during the Pacing state, it uses an On Update node combined with a sine wave calculation to make the NPC continuously walk back and forth. When transitioning to the Angry state, the On Enter State node instantly halts the movement and activates a hidden UI explosion graphic behind the character. Also, I deleted some of the useless attributes for the player. 
The most significant architectural update is how this State Machine interacts with the Dialogue/Narrative Engine. Instead of hardcoding state transitions within the state machine itself, it is driven by the dialogue text file. When the player clicks to advance the conversation, the Dialogue Engine parses the .txt script. If it detects a custom tag like [Event]|GoAngry, a String Split node isolates the command and fires a Trigger Custom Event aimed directly at the NPC's GameObject. The NPC's State Machine listens for this specific signal to transition between states.

## Milestone 3 Devlog
1. Instead of using static textures, this Unlit URP shader generates the blizzard dynamically in the Fragment stage by manipulating UV coordinates. It works by taking a base wind speed and applying standard Time for the downward fall, alongside Sine Time to create a horizontal, wobbling turbulence. These are combined to drive a Tiling And Offset node, which scrolls the UVs through a Voronoi noise generator. Finally, I use One Minus to invert the noise and a Power node to heavily increase the contrast, sharpening the blurry cells into distinct, swaying snowflakes

## Final Devlog
1. Our core gameplay design centers around a visual novel. Originally, our planned core loop was: interacting with NPCs -> prompting NPCs to drop specific items -> players collecting and synthesizing these items -> unlocking deeper interactions. Although the complete loop of item dropping, collecting, and synthesizing was not fully implemented in this Vertical Slice, we successfully developed the foundational dialogue engine, dynamic branching narrative, and the core UI framework. This implemented content still clearly illustrates the full game's vision to the player: it establishes the narrative-driven and choice-based nature of the game, setting the stage for the depth of interaction that will be present once the complete item synthesis and progression systems are fully integrated.

2. [C# file](https://github.com/p1ziYu/VerticalSlice/blob/main/My%20project/Assets/Shader/HoverBorderController.cs)
    Our UI hover glow border effect is activated directly from player interaction logic using Unity's Event System and a custom C# script. The script is attached to the button's Image child object and inherits from the IPointerEnterHandler and IPointerExitHandler interfaces. When the player hovers over the button, the script triggers an event and the Update() function calculates a smooth alpha transition, passing it to our custom Sprite Unlit Shader Graph. The script instantiates an independent material instance in Start(). Inside the Shader Graph, this alpha value is multiplied by an SDF (Signed Distance Field) border mask calculated in real-time using UV coordinates and a Smoothstep node

3. When breaking down a large project, I prefer combining bubble diagrams with step-by-step task breakdowns. I plan to continue using bubble diagrams because they intuitively map out the data flow and dependencies between different modules, such as Player states, NPC interactions, and underlying Systems. This planning process heavily influenced our Vertical Slice and highlighted a weakness because our workload estimation was overly optimistic. Consequently, we couldn't implement those features due to time constraints. This outcome taught me that future development requires much stricter task breakdowns.
